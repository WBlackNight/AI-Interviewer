## 0. 一句话结论

四个 LLM 组件的**失败不再静默**：每次调用都按
`llm_success / heuristic_fallback / error_raised` 分类记账，

## 1. 步骤 2.1 真实调用与可观测回退

### 1.1 交付

| 文件 | 职责 |
|---|---|
| `app/llm/errors.py` | 错误分类（`LLMErrorKind` 十类）+ `retryable` 判定 + `as_llm_error` |
| `app/llm/telemetry.py` | 线程安全计数：三种结局互斥、按错误类别分组、命中率与平均延迟 |
| `app/llm/budget.py` | 每场面试的用量预算（ContextVar 传递，跨轮次累计） |
| `app/llm/resilience.py` | 统一回退策略：`call_with_fallback` / `handle_fallback` / `record_success` / `configure_strict` |
| `app/llm/client.py` | 有限重试（仅可重试类别）+ 并发上限 + token 记账 + 错误分类抛出 |
| `app/api/routes.py` | `GET /api/diagnostics/llm`：分项计数、缓存统计、预算配置 |
| `evals/llm_ping.py` | 对四个组件各做一次最小真实调用并报告 |

### 1.2 关键设计决策

**（a）预算超限不参与回退。** `BudgetExceeded` **不继承** `LLMError`，
在回退策略里显式穿透。若把它当成供应商故障回退，预算保护会静默失效——
"超预算"会变成"继续花钱跑启发式"，这比不设预算更糟。

**（b）只重试可重试类别。** 4xx / 密钥错误 / 输出格式错重试无用，
只会把"配置错误"伪装成"偶发故障"，并浪费配额。

**（c）金额只在配置单价表时计算。** token 数取自响应 `usage`（事实）；
**本项目不内置任何模型价格**——凭空填价格会伪造出看似精确的成本数字。
未配置单价时明确输出"不计算金额"。

**（d）严格模式用模块级开关而非构造参数。** 组件在工厂里被大量实例化，
走构造参数就得给每个组件加一条线，反而更容易漏掉某一个。

**（e）`on_success` 只在模型成功时回调。** 评分缓存挂在它上面。
若在函数返回后无条件写缓存，一次偶发失败产生的启发式结果会被固化，
把短暂的降级变成长期劣化。

### 1.3 `llm_ping.py` 的退出码语义

| 退出码 | 含义 |
|---|---|
| 0 | 四个组件均通过真实模型调用 |
| 1 | 有组件回退或报错（附类别，且明确提示"不可标注为 LLM 验证成功"） |
| **2** | **未配置密钥——未测试，不等于通过** |

隐私：只用合成题目/回答/简历；报告不含密钥、完整 URL 与简历内容（只打印长度与条数）。
延迟仅 1~3 次采样，脚本自己声明"只能用于发现连接问题，不能作为性能指标"。

## 2. 步骤 2.2 评分证据与质量

### 2.1 交付

| 文件 | 职责 |
|---|---|
| `app/agent/score_schema.py` | 严格 schema（`ScorePayload`）+ 跨字段校验 + 结构化证据 |
| `app/agent/integrity.py` | 提示注入检测与处置口径、实质内容判定 |
| `app/agent/score_cache.py` | 六要素组合键 + 有界 LRU + TTL + 命中率统计 |
| `app/domain.py` | 新增 `EvidenceRef`，`ScoreResult.evidence_refs`（可选字段，不落库） |
| `app/agent/scorer.py` | 启发式加注入处置；LLM 路径改走严格 schema 与缓存 |
| `app/config.py` | `SCORING_CACHE_*` 三项 |

### 2.2 严格 schema 覆盖的拒绝面

`extra="forbid"` + `strict=True` + 字段校验器，逐项对应评审要求：

- 总分与每个维度：**有限的 0–10**，拒绝 NaN / 负数 / 超界；
- **布尔值单独拦**（Python 中 `bool` 是 `int` 子类，会让 `True` 冒充 `1.0`）；
- 维度键必须**恰好**是三个（多一个少一个都拒绝）；
- 要点列表必须是**非空字符串、无重复**；
- 锚点必须**属于当前题**（假锚点的入口）；
- 命中与缺失**不得重叠**。

### 2.3 证据：位置 + 锚点映射

`EvidenceRef(anchor, quote, start, end)`：

- `quote` 必须**逐字出现在回答中**（拒绝伪造），`start/end` 由查找得到；
- 每条引用必须**映射到具体锚点**（按要点原文或其关键词匹配）；
- 命中的要点必须有引用支撑，否则拒绝；
- 证据字符串也带上位置（`锚点「原话」@start-end`）——字符串是唯一落库的部分，
  这样报告里能看到位置。

**边界（必须如实声明）**：这套检查能证明"引用真实存在且落在某个锚点上"，
**不能证明推理正确**——模型完全可能引用真实片段却得出错误结论。
它只用于拒绝明显伪造与结构异常，评分质量仍需人工标注评测（P4 的 κ 目标）。

### 2.4 提示注入的处置口径

刻意区分两种情况，避免误伤诚实候选人：

| 情况 | 处置 |
|---|---|
| 检测到注入**且无锚点命中** | 硬性压到 3 分以内（纯操纵） |
| 检测到注入**但有锚点命中** | 不扣分，仅在证据里标注（保持透明可审计） |

误报的代价不对称：误压分伤害诚实候选人，漏压分只是让一段无效文本拿到低分。

### 2.5 缓存

键包含**六项**：题目 id、锚点版本摘要、回答摘要、模型 id、提示词版本、评分配置摘要。
任一变化 → miss。有界 LRU + TTL + 命中率统计。**默认关闭**，
让"无缓存重复评测"成为基线口径。

⚠️ 两条如实声明：命中缓存的两次评测**连模型都没调用**，不构成可重复性证据；
缓存只写**模型成功**的结果。

## 3. 过程中发现并修复的缺陷（4 项）

| # | 缺陷 | 性质 | 影响 |
|---|---|---|---|
| 1 | `handle_fallback` 只在 `except` 里记录，**成功路径不记录** | 设计疏漏 | planner/resume_parser 在遥测里完全没条目 → 被诊断为 `not_run`，把"一直好用"误报成"从未运行" |
| 2 | 无命中场景下仍**强制要求引用映射到锚点** | 逻辑自相矛盾 | 一个锚点都没命中时，引用按定义无法映射 → 模型**永远无法合法地给出低分** |
| 3 | 删除 `LLMScorer._validate` 导致 **9 个既有契约测试失败** | 我引入的回归 | 已把这些用例改为调用新的 `ScorePayload + build_score_result`，**保留原意图**（非法载荷必须被拒绝），不是删测试 |
| 4 | 测试里 monkeypatch 目标过时（组件已不再直接 `import get_telemetry`） | 测试缺陷 | 断言到了一份空计数，测试"通过"但没验证任何东西 |

第 1、2 项都是由**测试**发现的，不是代码审查发现的——它们不会报错，只表现为信号失真与
某个分支永远走不到。第 4 项尤其值得警惕：**一个验证了空气的测试比没有测试更危险**。

## 6. 运行方式

```bash
cd backend && .venv\Scripts\activate

# 全量测试
python -m pytest -q

# 真实连通性探测（未配置密钥时退出码 2）
python ../evals/llm_ping.py
python ../evals/llm_ping.py --repeat 3 --json-out ping.json
python ../evals/llm_ping.py --strict        # 直接暴露原始错误类别

# 进程内计数与缓存统计
curl --noproxy '*' http://127.0.0.1:8000/api/diagnostics/llm
```

启用评分缓存（默认关闭）：

```
SCORING_CACHE_ENABLED=true
SCORING_CACHE_MAX_ENTRIES=512
SCORING_CACHE_TTL_SECONDS=3600
```

# 错误经验总结与编码规约

汇总自：P1 语音链路实现（2026-10-12）、旧库 schema 迁移修复（2026-10-12）、
以及更早的 P0/P0.1 修复与两轮评审。

用法：**改代码前扫一遍第三节的规约清单**；每条规约都来自一次真实故障，
不是假想风险。新增经验时请沿用「现象 → 根因 → 规约」三段式。

---

## 一、缺陷模式分类（按根因）

### 1. 顺序型：先置空/覆盖，后使用

P1 一轮里出现 **3 次**，是最容易出现、也最难靠肉眼发现的模式。

| 现象 | 根因 |
|---|---|
| 语音轮次完全不播报 | `start_turn()` 内硬编码 `self._from_voice = False`，覆盖了调用方刚设置的 `True` |
| 题目全部静音 | 播放侧只读 `event["text"]`，而 `question` 事件用的是 `content` |
| `t_vad_end` 时间戳永远缺失 | `finish()` 里先 `self._t_vad_end = None`，之后才判断 `if self._t_vad_end is not None` |
| `turn_id` 拿到空串 | 在 `finish()` **之后**取 `self.voice.turn_id`，而 finish 会清空发言绑定 |

共同点：**取值/使用的位置晚于状态清理的位置**。

**规约 R1**：清理状态（置 None、重置标记、`pop`）必须放在**所有读取之后**，
最好结尾统一写 `finally` 式清理；若中途需要清理，先把值取到局部变量。

**规约 R2**：方法间传递的上下文（如"这次调用是语音来的"）一律用**显式参数**，
禁止用实例属性做隐式通道——属性会被同一方法路径上的其他赋值覆盖。

### 2. 状态复位型：一次性标记未复位

| 现象 | 根因 |
|---|---|
| 第二段发言的识别结果永远提交不出去 | `_final_submitted` 置 True 后未在新发言开始时复位 |

**规约 R3**：任何"只允许发生一次"的标记，都必须在其生命周期起点显式复位，
并配一条"发生第二次"的回归测试。不要依赖"反正不会再发生"。

### 3. 副作用时机型：副作用先于判定

| 现象 | 根因 |
|---|---|
| 一次咳嗽就建立 ASR 会话 | 通道用 `state == SPEECH` 判断，而"是否真的在说话"需要 VAD 的 `armed`（最短语音时长门槛） |

**规约 R4**：判定条件要用**语义正确的那个状态**，不要用"看起来差不多"的邻近状态。
不确定时把该状态显式暴露到接口上（本例改成 `VAD.armed` 协议方法）。

### 4. 字段契约型：生产端与消费端字段名不一致

见上表"题目全部静音"。

**规约 R5**：跨模块传递的数据结构，字段名只允许在一处定义，消费端用**归一化函数**
读取（如 `event_text()` 同时接受 `text`/`content`）。新增字段时先搜消费端。

### 5. 测量方法型：用推算代替实测

| 现象 | 根因 |
|---|---|
| 延迟探针算出 **−753ms** 负延迟 | 用 `started + (n-1)×100ms` 公式推算"用户停口"时刻，但帧是一次性灌完的，真实时刻远早于公式值 |
| `vad_to_asr_final` 恒为 0 | 客户端在同一事件上对两个语义不同的事件打点，是伪指标 |

**规约 R6**：任何延迟/耗时指标都必须来自**真实时钟打点**，不得用公式推算。
推算值在并发、批处理、IO 抖动下必然失真，且方向不固定（会得到看似离谱的负值）。

**规约 R7**：跨机时钟不可相减。服务端段用服务端单调时钟，浏览器段由前端打点，
**分列呈现**；未测量的项明确写"未测量"，不用相邻数字冒充。

### 6. 测试自身缺陷

| 现象 | 根因 |
|---|---|
| 断言"取消后不再有新分片"偶发失败 | 断言了"已交给发送协程的在途帧"，而这是分布式语义下**不可保证**的 |
| `LIKE 'interview__%'` 误匹配 `interview_event` | SQL 的 `LIKE` 中 `_` 是单字符通配符 |
| 迁移测试"库里 11 张表都不存在" | 在**同一个 cursor 上嵌套 execute**，外层迭代被重置，只扫到第一张表 |
| 迁移报 `NoReferencedTableError` | `to_metadata(新MetaData)` 只复制了单表，外键目标表不在同一 MetaData |

**规约 R8**：断言只能覆盖**实现真正能保证的东西**。做不到的（在途网络帧、第三方
时序）要写进注释说明边界，并说明由谁兜住（本例：前端在 `barge_in_ack` 时清空缓冲）。

**规约 R9**：SQL 里用精确值或 `ESCAPE`，不要用 `LIKE` 拼"看起来安全"的模式。

**规约 R10**：**先 `fetchall()` 再遍历**。同一 cursor 上嵌套执行会重置外层迭代。

**规约 R11**：SQLAlchemy `to_metadata` 复制含外键的表时，必须按
`Base.metadata.sorted_tables` **整体复制**到同一 MetaData，否则外键无法解析。

### 7. 输出自相矛盾 = 工具在骗你

上面的 cursor 缺陷之所以被发现，是因为输出**自相矛盾**（一边说表都存在，一边说都不存在）。

**规约 R12**：工具输出与已知事实冲突时，先怀疑工具，再怀疑结论。
交叉验证一次（用另一种方式取同一个事实）比继续往下推理便宜得多。

## 二、环境类坑（本机可复现）

| 现象 | 原因 | 处理 |
|---|---|---|
| `pip install` 报 403 / `versions: none` | 环境设了 `http_proxy`，代理按白名单只放行官方源 | 用 `-i https://pypi.org/simple`；**不要**换国内镜像（会被拒） |
| `metadata-generation-failed` → `pydantic-core`，`WinError 193` | Python **3.14** 下该项目 pinned 的 `pydantic-core` 无预编译 wheel，回退源码编译又缺 Rust | 用 Python **3.12/3.13**；`X` 不能被代理/镜像问题掩盖 |
| 本地 HTTP 返回 502 | `http_proxy` 把 `127.0.0.1` 也代理了 | `curl --noproxy '*'`；Python 用 `ProxyHandler({})` |
| CMD 报 `'.venv' 不是内部或外部命令` | CMD 只认反斜杠，`/` 被当命令开关 | `.venv\Scripts\activate.bat`（PowerShell 用 `Activate.ps1`；Git Bash 才用 `source`） |
| 创建面试报 `NOT NULL constraint failed: interview.user_id` | `create_all` **只建缺失的表，不演进已有列**；旧库 schema 停留在模型改动之前 | 启动迁移已修复；逃生通道是删除 `dev.db` 重建 |
| 服务端改了代码但行为没变 | uvicorn 未开 `--reload` | 验证前确认进程是用新代码启动的 |

**规约 R13**：报错信息常常只指向**症状**。本次"装不上依赖"的真因经过三层：
表象（卡死）→ 二次（`versions: none`）→ 根因（代理 403）。**不要停在第一层就动手改。**

**规约 R14**：改了服务端代码后，验证前必须重启进程；否则会得到"改了没用"的错误结论
（本轮 `t_vad_end` 缺失排查时就踩过）。

## 三、改代码前的规约清单

改任何代码前逐条自问：

1. **R2** 有没有用实例属性做隐式上下文通道？→ 改显式参数
2. **R1** 清理状态的代码是否在所有读取之后？
3. **R3** 新增的"一次性标记"是否有复位点和"第二次"测试？
4. **R4** 判定条件是不是语义正确的那个状态，而不是邻近状态？
5. **R5** 新增/改动的字段名，消费端都跟上了吗？
6. **R6/R7** 指标是真实打点吗？跨机时钟分列了吗？
7. **R8** 断言的是实现**能保证**的事吗？保证不了的边界写注释了吗？
8. **R9/R10/R11** SQL 与 ORM 工具的使用是否踩了 `LIKE` 通配符 / cursor 嵌套 / `to_metadata`？
9. **R13** 我停在了第一层症状，还是找到了根因？
10. **R14** 验证前重启进程了吗？
11. **R15** 埋点覆盖了成功路径吗？还是只记了异常分支？
12. **R16** 校验规则互推过吗？有没有"恒不成立"的条件？
13. **R17** 断言前确认过"真的产生了数据"？monkeypatch 目标在重构后还对吗？
14. **R18** 删成员前查过测试引用吗？——改测试的调用点，但**保留原断言**。
15. **R19** 插入新类有没有留下重复/孤立装饰器？

## 四、值得保留的机制

### 1. "不得把未验证能力写成已具备"

两轮评审反复强调这一点，且实践证明它有效：
P1 交付里刻意区分了"协议与管道已验证"与"真实供应商未接入 / 浏览器未实测 / VAD 未校准"。
这让后续排期能基于真实状态做，而不是基于乐观叙述。

**延续做法**：每份实现记录都写一节「明确未完成（不得声称已具备）」。

### 2. 用测试守护修过的顺序缺陷

顺序型缺陷修完后极易回归（它们不报错，只表现为行为变怪）。
本轮为时间戳缺失/倒置专门加了 `TestVoiceTimestamps`，断言字段存在且两戳不倒置。

**延续做法**：每个顺序型缺陷修复后，补一条只针对该顺序关系的断言。

### 3. 先审计再动手

迁移前先做了全库 schema 审计，确认**只有一处差异**，才敢用定点迁移。
若当时贸然写一个"大而全"的迁移，风险与验证成本都会失控。

**延续做法**：数据/结构类改动前，先用只读脚本把差异量化，再决定方案。

### 4. 破坏性操作前先备份

迁移前 `dev.db → dev.db.bak-20261012-231937`，升级后逐表比对行数不变。
成本几乎为零，但把"不可逆"变成"可回滚"。

**延续做法**：任何可能丢数据的操作前先备份，并把备份路径写进交付说明。

## 五、P2 新增经验（2026-10-12）

### 8. 只在失败分支埋点 → 成功路径不可见

| 现象 | 根因 |
|---|---|
| planner / resume_parser 在遥测里完全没有条目，被诊断为 `not_run` | 这两个组件用 `except` 分支里的 `handle_fallback` 记录，**成功路径什么都没记** |

比"记录不到"更糟的是**方向性错误**：它把"一直好用"报成"从未运行"，
排查时会朝完全错误的方向走。

**规约 R15**：埋点必须覆盖**所有结局**（成功 / 降级 / 抛错），不能只记异常分支。
新增一个 `except` 记录点时，同时问一句"成功路径谁记？"

### 9. 自相矛盾的校验条件

| 现象 | 根因 |
|---|---|
| 模型永远无法合法地给出低分 | 要求"每条引用必须映射到锚点"，而"一个锚点都没命中"时引用按定义无法映射 |

同一份校验里，条件 A（无命中）使条件 B（引用必须映射）恒不成立。
它不会抛错、不会崩，只会让某个合法分支**永远走不到**，表现为"总是降级"。

**规约 R16**：写校验规则时逐条互推一遍——在每条规则假设的前置条件下，
其他规则是否仍然可能成立？出现"恒不成立"就说明规则集自相矛盾。

### 10. 验证了空气的测试

| 现象 | 根因 |
|---|---|
| 测试"通过"，但断言的是空字典 | monkeypatch 打在组件模块的 `get_telemetry` 上，而重构后组件已改为从 `resilience` 取遥测 |

**一个什么都没验证的测试比没有测试更危险**：它给出虚假的安全感，
让人以为覆盖到了。

**规约 R17**：断言前先确认被测对象**真的产生了数据**（例如断言字典非空、计数 > 0）。
替换点（monkeypatch 目标）在重构后必须跟着改——重构时把"测试里 patch 了谁"一并检查。

### 11. 删除被测试引用的私有成员

| 现象 | 根因 |
|---|---|
| 9 个既有契约测试失败 | 把校验逻辑从 `LLMScorer._validate` 抽到新模块，直接删了原方法 |

这是**引入的回归**，而不是测试过时。

**规约 R18**：删除任何成员前先查引用（含测试）。若被测的是"契约"而非"实现位置"，
应当**把测试改为调用新入口、保留原断言**，而不是删除或放宽测试。
删测试等于悄悄降低质量标准。

### 12. 装饰器叠加

| 现象 | 根因 |
|---|---|
| `TypeError: Cannot overwrite attribute __setattr__` | 编辑时新插入的 `@dataclass(frozen=True)` 与原有装饰器叠加成两个 |

**规约 R19**：用 Edit 插入新类时，`old_string` 要包含**上一个类的装饰器之前**的上下文，
避免留下孤立的或重复的装饰器；改动后立刻跑一次导入自检。

### 步骤 1.1 先定音频协议

**落点**：`domain.py`、`api/ws.py`、`frontend/lib/types.ts`、`voice/` 与协议测试均已存在。下例为协议形状；turn_id须为当前问题的32位十六进制ID。

```jsonc
// 拟新增上行：每次语音回答一个 turn_id，seq 在该流内递增
{"type":"audio","turn_id":"0123456789abcdef0123456789abcdef","seq":0,"format":"pcm_s16le","sample_rate":16000,"channels":1,"data":"<base64>"}
{"type":"audio_end","turn_id":"0123456789abcdef0123456789abcdef"}
{"type":"interrupt","utterance_id":"u-17"}
// 拟新增下行
{"type":"asr_partial","turn_id":"0123456789abcdef0123456789abcdef","text":"B+树"}
{"type":"asr_final","turn_id":"0123456789abcdef0123456789abcdef","text":"B+树是……"}
{"type":"tts_chunk","utterance_id":"u-17","seq":0,"format":"pcm_s16le","sample_rate":24000,"channels":1,"data":"<base64>"}
{"type":"tts_end","utterance_id":"u-17"}
{"type":"barge_in_ack","utterance_id":"u-17"}
```

采集规格建议先选 16kHz、单声道、PCM16 little-endian、100ms 网络帧：**1600 个样本 = 3200 字节，base64 为 4268 字符**，不含 JSON。原文“3200 样本/100ms”有误。TTS 采样率按供应商协商并在协议中明示，不默认等于 ASR 采样率。

同一 WS 保持有序，seq 主要用于检测重复、断线恢复及应用层并发差错；出现缺口应记录并重置/补齐该流，不可悄悄丢音频。校验 base64、帧大小、采样率、总时长，增加队列上限和背压；慢客户端不能无限堆积内存。

**验收**：已有 `tests/test_ws_protocol.py` 覆盖协议；Dummy 只证明协议可用。真实音频仍按本节门槛验收。

### 步骤 1.5 打断

**目标**：用户开口到本地停止播放的 P95 < 300ms（拟定），并另报服务端 ACK 延迟。

不能使用连续三个 100ms 帧才触发作为达标依据：检测已耗尽 300ms，还没有留下处理与播放缓冲预算。建议独立使用 10–20ms 检测窗并实测调阈值。检测到打断时本地立即静音并清空该 utterance，随后通知后端取消生成/合成/发送；收到已取消 utterance 的迟到包也丢弃。

播放状态与面试业务状态分离。启用设备支持的回声消除并测试外放；**全程暂停服务端 VAD 会失去服务端打断检测**，不能同时宣称“双保险全双工”。若外放条件暂不能可靠处理，明确采用耳机模式或按住说话的半双工方案。

**验收**：播放中说话、连续打断、自然播放结束、外放回声、后台慢响应、打断后立即回答、断线、迟到音频均有用例；持久化 utterance 取消事件及原因。

### 步骤 2.2 评分证据与质量

- 将评分、维度、命中/缺失要点、证据定义为严格 schema。总分和每个维度均须为有限的 0–10 数值，禁止 NaN、负数和假锚点；锚点 ID 必须属于当前题。
- evidence 使用回答原文片段及位置，并映射具体评分锚点。检查片段是否存在只证明引用真实性，不能证明推理正确；仍需人工标注评测。
- 空回答、否定句、关键词堆砌、提示注入和“我不会”不能仅因长度或关键词得到高分。简历和回答属于待评估数据，不得作为指令覆盖评分规则。
- 追问应在生成时携带目标节点和评分要点；已改为目标节点与独立锚点；后续补充语义质量评测，不能只依靠关键词。
- 如加缓存，键应包含题目/锚点版本、回答内容摘要、模型与提示词版本、评分配置；使用有界缓存和保留策略。固定 temperature 不保证外部服务跨时间完全一致，缓存一致性也不等于评测可重复性。

**验收**：异常字段和伪造 evidence 被拒绝/回退；验证回退原因可观察；缓存失效与无缓存重复评测分开。κ ≥ 0.7 为拟定目标，定义见 P4。

### 步骤 2.3 PDF 接口与隐私（2026-10-21 已实现基础链路）

## 五、P4 评测体系（随开发推进）

现有 `evals` 包含 `smoke_e2e.py`（支持`--pdf`、`--retrieval`及显式`--embedding-provider zhipu`）、`embedding_ping.py`、`llm_ping.py`、`latency_probe.py`、`build_question_index.py`、`retrieval_eval.py`。下表除latency_probe/retrieval_eval外均为拟新增；smoke数据不替代独立质量评估，示例数值不得写成真实指标。

| 脚本 | 输入与方法 | 输出与验收口径 |
|---|---|---|
| `latency_probe.py` | 固定音频/回答、模型、设备、网络条件；分冷启动/热态、并发档位 | P50/P95、失败/超时率、样本量；用户停口→播放与 VAD确认→播放分列 |
| `wer_eval.py` | 人工参考转写、真实 ASR、归一化规范 | 中文 CER=(替换+删除+插入)/参考字符数；WER 的分母是词数，需固定分词；另报术语错误 |
| `scorer_agreement.py` | 同一题与回答由 AI 和多位独立评分者盲评 | 明确量表及离散化规则、加权 Cohen κ、Spearman、95% CI 和人类两两一致性 |
| `probe_hitrate.py` | 人工独立标注追问是否针对具体缺口 | 命中率、Wilson 95% CI、标注一致性；关联轮次按会话聚类处理 |
| `retrieval_eval.py` | 固定查询、候选库、人工相关性判断 | BM25/向量/RRF/rerank 的效果、延迟和成本对照 |
| `ablation.py` | 同一模型、题库、种子和输入集，逐个移除组件 | 追问质量、评分一致性、延迟、成本、流程违规/未完成率 |
| `pack_bench.py` | 题目、参考答案、锚点、用例、录音、来源/许可 | JSONL schema、版本、校验值、datasheet、拆分清单 |

**统一约束**：

- HTTP/WS 脚本不能独自观察用户实际听到的音频，需要浏览器播放打点；服务端和浏览器时钟不可直接相减，采用各自单调时钟、可说明误差的同步/关联方案。记录排队、评分、追问生成、TTS、传输、播放等阶段，不能漏掉评分耗时。
- 中文“字错率”是 CER，原文误称 WER。安静房间单人录音只能做基线，正式评测应增加说话人、设备、语速和噪声条件，并保留独立测试集。CER <5% 是拟定目标，需同时报告测试条件。
- 评分一致性目标 κ≥0.7。先定义评分者资格、量表和聚合规则；Cohen κ 用于两位评分者/两个评分序列，多评分者可列两两 κ 或选合适统计量。按会话/受试者聚类 bootstrap，避免把同一场追问当独立样本。人类一致性是参照，不是数学意义上的绝对上限。
- 追问命中率目标 ≥80%；100 组可作为初始评测规模，报告 CI，不能仅给点估计。三人独立标注后仲裁并保存分歧。
- 纯 LLM 无状态机对照需保留消息/成本/轮数硬上限；不完成样本计入失败率，不能从平均结果中删掉。
- 20 条示例可调试脚本，30 场面试可做初步研究，规模应依据估计精度和资源确定；固定种子不能保证远程 LLM 完全确定。
- Bench 目标 200 题需要先扩充数据，当前只有18题；按题目/会话分组划分开发与测试集，防止参考答案泄漏。代码正确性合成回答只用于冒烟，不用于证明真实面试评分有效。

**P4 完成条件**：每个指标都有原始数据、运行配置、版本、失败统计与可复算报告；所有对比共享输入条件，不宣称没有数据支持的显著性或因果改进。

当前动态路径 `/interview/[id]`、`/report/[id]` 在 build 中为动态路由，配置没有静态导出。建议 Nginx → **Next.js Node 服务** 和 FastAPI，API/WS 由 Nginx 转发；不能把 `.next` 当静态站点目录直接交给 Nginx。[Next.js 14 部署文档](https://nextjs.org/docs/14/app/building-your-application/deploying)

拟新增前后端 Dockerfile 与 `docker-compose.prod.yml`，固定镜像/运行时、健康检查、重启策略和日志轮转。前端公开地址在构建前配置；WS 反代配置 Upgrade/Connection 与读超时。真实域名使用 HTTPS/WSS。

PostgreSQL 需补驱动、版本化迁移、备份与恢复演练；Redis/Qdrant 仅在功能实际需要时部署。启动缓存不是迁移方案，`create_all` 不会自动演进已有列。4C8G 只能作为待压测候选，不能保证同机语音模型、reranker、数据库和沙箱的容量。

### 步骤 5.2 公开访问前的工程门槛

- 身份与资源归属：简历、面试、报告、WS 均校验用户/会话凭据；随机 ID 和 CORS 不代替授权，WS 单独校验 Origin。
- 数据生命周期：明确收集内容、外部模型处理、保留期限、删除与导出；日志脱敏，密钥仅在服务端，备份也需纳入删除与访问策略。
- 稳定性：限流/成本限额、健康与依赖 readiness 分开、错误观测、过期会话回收、单 worker 容量与多 worker 策略、依赖安全审计和故障演练。
- 公网发布涉及的备案、隐私及生成内容标识要求，应按实际服务范围和发布地区在上线时核对；本文不再用某份法规名称或“一张声明页”作为已合规结论。

**验收**：跨用户访问被拒、删除可验证、备份可恢复、供应商故障可回退、WS 重连测试通过、容量和成本有实测记录。

### 步骤 5.3 用户验证与提交物

≥100 注册、≥200 场、SUS≥75 作为内部目标。当前已有本地用户名注册/登录；每次简历上传创建的User行仍不是账户，不能当注册数。Account行可统计账户数，但未做人类身份核实/去重，仍需定义真实参与者、漏斗和完面口径。

历史能力画像表目前仅有 ORM 定义，没有更新和消费链路；“首次与第三次提升”应控制题目难度/重复练习影响并报告样本流失，不能仅凭产品自己的评分曲线宣称训练有效。

拟新增用户指标脚本，保存问卷、授权与脱敏案例。答辩视频时长和提交清单以实际赛事通知为准；准备运行手册、真实测量报告、可复现示例、离线资源及演示录屏，不把尚未实现的功能画成已交付架构。

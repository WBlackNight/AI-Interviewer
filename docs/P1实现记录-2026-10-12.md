## 0. 一句话结论

**语音链路的骨架已打通并自动化验证**：音频帧 → VAD → ASR → 复用既有 turn 提交 → 事件下发 → TTS 分片 → 前端播放缓冲。
**但这不是"语音功能已完成"**：真实识别/合成供应商未接入，浏览器未真机实测，VAD 阈值未校准（详见 §5）。

## 1. 交付内容

### 1.1 协议（步骤 1.1）

`app/schemas.py` 新增严格校验的上行消息，与既有 `StartMessage/AnswerMessage` 同属 discriminated union：

| 消息 | 关键约束 |
|---|---|
| `audio` | `turn_id` 32 位十六进制、`seq` 单调递增、`format/sample_rate/channels` 用 `Literal` 锁定为 `pcm_s16le/16000/1`、`data` 长度 ≤ base64(6400B) |
| `audio_end` | 客户端主动结束发言（按住说话/松开） |
| `interrupt` | `utterance_id` 可省略（打断可能早于首个 `tts_chunk` 到达） |

`app/domain.py` 新增下行事件常量与 `VoiceRecordType`（只落库、不下发的审计类型）。
音频规格按评审修正：**1600 样本 = 3200 字节 = base64 4268 字符**（原稿"3200 样本"有误）。

### 1.2 后端语音模块（`app/voice/`）

| 模块 | 职责 | 关键点 |
|---|---|---|
| `audio.py` | 帧编解码与校验 | 坏 base64 / 非样本整数倍 / 超限均**抛明确异常**；`rms` 用整数平方和避免浮点漂移 |
| `vad.py` | VAD 与前置缓冲 | `EnergyVAD` 零依赖确定性；`PrerollBuffer` 防丢首字；`SileroVAD` 为**待联调骨架**并写明 512 样本窗口要求 |
| `asr.py` | 识别会话 | `start/feed/finish/close`；`DummyASR.finish` **只返回一次**（对应 final 单次提交）；`XfyunASR` 待联调 |
| `tts.py` | 合成 | PCM 分片，采样率协议明示；`DummyTTS` 输出静音（**不算语音成功**），`EdgeTTSClient` 待联调且需先解决 mp3→PCM |
| `utterance.py` | 切句与文本流 | `event_text()` 统一 `text`/`content` 字段差异；`split_sentences` 支持句末标点、次级断点、长文本硬切 |
| `channel.py` | 上行编排 | 帧序校验、缺口重置、前置缓冲、final 单次提交、超长收束 |
| `playback.py` | 下行编排 | 有界队列 + 取消令牌 + 迟到分片丢弃 + 背压放弃 + 审计落库 |

### 1.3 WS 三任务架构（步骤 1.4）

`app/api/ws.py` 重构为三个独立任务：

1. **接收**：只做校验与路由，不阻塞在业务处理上；
2. **业务处理**：每轮后台协程 + `asyncio.to_thread(process_message)`；
3. **音频发送**：`PlaybackController` 内部协程，从有界队列取分片。

配套：`WSender` 用锁串行化发送（业务事件、音频、错误来自不同协程，不串行会在传输层交错）；
音频帧使用**独立频率预算**（默认 900 帧/分钟），否则 10 帧/秒会在 6 秒后撞上文字消息的 60 条/分钟限流。

对既有语义的保持：文字模式行为不变（含 `interrupt` 的提示语）；同一连接内轮次串行（新消息到达先 `await` 在飞轮次）。

### 1.4 前端通路（步骤 1.2/1.5）

| 文件 | 内容 |
|---|---|
| `public/worklets/voice-processor.js` | `capture-processor`（拷贝后 post，避免缓冲复用）+ `playback-processor`（有界队列，满则丢最旧） |
| `lib/pcm.ts` | 低通 + 线性插值重采样、s16le↔Float32、base64、`FrameAssembler` |
| `hooks/useVoiceChannel.ts` | 真机采样率重采样、100ms 成帧、**20ms 独立打断检测窗**、有界播放缓冲、设备断开处理 |
| `hooks/useInterviewSession.ts` | 新增语音事件分流（不进聊天流）、`subtitle`、`sendVoice`、`registerVoiceSink` |
| `components/VoicePanel.tsx` | 麦克风开关、电平、播报/打断、字幕、**始终可见的文字回退提示** |
| `app/interview/[id]/page.tsx` | `NEXT_PUBLIC_VOICE_ENABLED` 开关（默认关，与后端一致） |

设计落点：重采样在**原生采样率上攒满 100ms 再转换**（避免逐块转换在边界产生不连续）；
`seq` 仅在发送成功时推进（否则服务端会判为缺口）。

## 3. 过程中发现并修复的缺陷（8 项）

验证阶段暴露的问题，全部已修并补测试：

| # | 缺陷 | 性质 | 影响 |
|---|---|---|---|
| 1 | `_final_submitted` 提交后未复位 | 逻辑 | **第二段发言的 final 永远提交不出去** |
| 2 | VAD 未武装就开启 ASR 会话 | 逻辑 | 一次咳嗽即建立识别会话（改为显式依赖 `armed`） |
| 3 | `speak()` 与 `_from_voice` 赋值冲突 | 顺序 | `start_turn` 覆盖调用方设置 → **语音轮次完全不播报** |
| 4 | `question` 事件用 `content`，播放只读 `text` | 字段不匹配 | **所有题目静音** |
| 5 | `turn_id` 在 `finish()` 后取值 | 顺序 | 拿到空串 → `AnswerMessage` 校验失败 |
| 6 | `_t_vad_end` 在构造事件前置空 | 顺序 | 时间戳字段永远缺失（探针拿不到服务端分段） |
| 7 | 探针共用一场面试 | 探针设计 | 面试有限，后续轮次无题可答 → 16.7% 失败率 |
| 8 | 探针用公式推算 `speech_stop` | 测量方法 | 帧未按节拍发送 → 算出 **−753ms** 负延迟 |

第 3、4、6 项都是"先置空/先覆盖、后使用"的顺序缺陷，因此第 5、6 项专门补了守护测试
（`test_voice_flow.py::TestVoiceTimestamps`），断言字段存在且两戳不倒置。

## 7. 旧库 schema 陈旧问题（**已修复**）

### 7.1 问题

`backend/dev.db` 的 `interview.user_id` 仍是 `NOT NULL`，而模型已改为可空。
`Base.metadata.create_all` **只建缺失的表、不会演进已有列**，于是不带 `resume_id`
创建面试时 `IntegrityError: NOT NULL constraint failed: interview.user_id`（HTTP 500）。

### 7.2 决策：加迁移，而不是删库重建

先做了全库审计，确认**只有这一处差异**（12 张表齐全，除该列外无缺列/多列/可空性差异）：

```
模型表数 12 / 库表数 12
  库缺表: 无      库多表: 无
列级差异: interview.user_id: 模型 nullable=True / 库 NOT NULL=True
总差异数: 1
```

选迁移的理由（四条，按重要性排序）：

1. **项目已经把迁移当作既定的 schema 演进机制**：`migrations.py` 已存在、`main.py`
   每次启动都会调用，`技术实现步骤.md` 也明确写了"`create_all` 不会自动演进已有列"。
   补一条迁移是顺着既有架构走，不是引入新机制。
2. **该缺陷不是本机独有**：任何在模型改动之前创建的库（同事克隆、预发库、
   将来切 PostgreSQL 的部署）都会以同样方式失败。删本地 `dev.db` 只修一台机器。
3. **只有迁移可被回归验证**：可以构造"旧 schema + 历史数据"的库，断言升级后可空、
   数据保留、索引重建、重复执行幂等。"删库"没有任何可测的面，同一个坑会再踩。
4. **dev.db 里有真实行**（4 用户 / 4 简历 / 3 面试 / 113 事件 / 22 条评分），
   且项目自身的升级说明就要求"升级前备份数据库"——本项目的取向是保数据，不是丢数据。

同时保留了"删库重建"作为逃生通道：若迁移在某种环境失败，`dev.db` 可直接删除
（`create_all` 会按当前模型重建），代价只是丢掉开发数据。

### 7.3 实现

`app/migrations.py::upgrade_interview_user_nullable(engine)`，在 `main.py` 启动时调用，
顺序为「先补 schema，再修历史数据」：

- **幂等**：表不存在或列已可空 → 直接返回 `False`，不做任何写入；
- **SQLite**：不支持 `ALTER COLUMN DROP NOT NULL`，按官方推荐的表重建
  （建新表 → 拷数据 → 删旧表 → 改名 → 重建索引），全程单事务，失败即回滚；
- **外键自检**：重建后跑 `PRAGMA foreign_key_check`，有违规就 `RuntimeError` 触发回滚；
- **自愈**：上次中断留下的临时表会被 `DROP TABLE IF EXISTS` 清掉；
- **PostgreSQL**：`ALTER TABLE interview ALTER COLUMN user_id DROP NOT NULL`。
  ⚠️ 该分支**未在本环境实测**（当前部署仍是 SQLite），只有 SQLite 分支有自动化覆盖。

### 7.5 过程中暴露的两个工具缺陷（已修）

- 首版审计脚本在**同一个 cursor 上嵌套执行 `PRAGMA table_info`**，导致外层迭代被重置、
  只扫到第一张表，输出自相矛盾（声称库里 11 张表都不存在）。改为先 `fetchall()` 再遍历。
- 首版迁移用 `table.to_metadata(新MetaData, name=...)` 只复制了 `interview`，
  其外键指向的 `user`/`resume` 不在同一 MetaData → `NoReferencedTableError`。
  改为按 `sorted_tables` 顺序整体复制，保证外键可解析。
